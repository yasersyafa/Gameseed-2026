## Architecture

Three orthogonal layers — they do not call each other directly. Wiring happens via DI (services) + a static event bus (gameplay signals).

### 1. DI: VContainer (`Scripts/DI/RootLifetimeScope.cs`)

`RootLifetimeScope` is the single scene-root scope. It registers **every persistent service** via `RegisterComponentInHierarchy<T>()`: `GameManager`, `RoundManager`, `LivesSystem`, `HitEffectManager`, `AudioManager`, `CinemachineCameraManager`, `SettingsManager`, `RumbleManager`. Without these registrations, `[Inject]` returns null everywhere (silent failure mode — empty target groups, no audio, etc.).

- Players spawn at runtime via `PlayerInputManager`. `GameManager.OnPlayerJoined` calls `_resolver.InjectGameObject(playerInput.gameObject)` so runtime players still receive `[Inject]`. Any new player-side service must be added to `RootLifetimeScope` AND consumed via `[Inject] Construct(...)` on the component.
- `RootLifetimeScope.Configure` also hooks `SceneManager.sceneUnloaded` → `GameEvents.ClearAll()` to prevent stale event subscribers across scene reloads.

### 2. Event bus: `GameEvents` (`Scripts/Core/GameEvents.cs`)

Static class with `Action`-typed events for player lifecycle, round lifecycle, combat (throw/catch/dash/charge/parry/wall-bounce), and pickups. Producers call `GameEvents.RaiseX(...)` helpers; consumers `+=` in `OnEnable`, `-=` in `OnDisable`. **Always pair subscribe/unsubscribe** — `ClearAll()` runs on scene unload but in-game code must not leak.

This is the canonical way to cross-cut systems (HUD listens to scores, AudioManager listens to combat events, RumbleManager to hits, etc.). Don't add direct references between e.g. `Boomerang` → `AudioManager`; raise an event.

### 3. Player FSM (`Scripts/Player/IPlayerState.cs` + `States/`)

`PlayerController` holds `IPlayerState _currentState` and forwards `OnMove/OnDash/OnThrow/OnAttack` (Unity Input messages) to it. States: `Idle`, `Charging`, `Attacking`, `Dashing`, `Frozen`, `Eliminated`. Transitions go through `player.ChangeState(new XState())`, which calls `Exit` → swap → `Enter`.

`SetFreeze(bool)` (called by `RoundManager` for countdown/round-end) and `SetEliminated(bool)` (called by `LivesSystem`) are the external state-change entry points. State classes own input handling — do not put input branching in `PlayerController` itself.

### Throw input quirk (important)

`PlayerInput` is configured in **SendMessages** mode. In that mode `OnThrow(InputValue)` only fires on Performed (press), not on Canceled (release), and `onActionTriggered` is unreliable. `PlayerController.Update()` therefore **polls** `_throwAction.IsPressed()` each frame and calls `_currentState.HandleThrowReleased(this)` on the down→up edge. If you change the throw input wiring, preserve this polling — the charge-throw release detection depends on it.

### Round / lives flow

`GameManager` (player joining, spawn, material, runtime injection) → on `minPlayersToStart` reached, calls `RoundManager.InitRound(count)` → `RoundManager` runs countdown coroutine, freezes/unfreezes players via `PlayerController.SetFreeze`, registers players with `LivesSystem`, raises `OnRoundStarted`. `LivesSystem.PlayerDied` decrements lives, hides/respawns or eliminates, and once `_alivePlayers <= 1` calls `RoundManager.OnRoundEnd(winnerIndex)` which increments score and either loops to next round or raises `OnGameOver` at `pointsToWin`.

### Config: ScriptableObjects override SerializeField

`PlayerController`, `Boomerang`, `RoundManager`, `LivesSystem` all carry a `[SerializeField] XSO statsSO`. If assigned, `Awake` calls `ApplyStatsFromSO()` / `ApplyConfigFromSO()` and overwrites the inspector-tuned `[SerializeField]` fields. This means **inspector values are ignored when an SO is assigned** — change the SO, not the prefab field, or you'll see no effect at runtime.

### Power-ups (`Scripts/PowerUps/`)

`PowerUpController` is a per-player stack of `IPowerUpEffect` (max 3 slots, mutex groups via `PowerUpSO.MutexGroup` so e.g. Fire/Ice cancel each other). `PlayerController.OnHitByBoomerang` calls `PowerUps.OnBeforeHit` first — effects can absorb the hit (Shield) and return true to skip damage. `PlayerController.ThrowBoomerangCharged` calls `PowerUps.OnBeforeThrow(boomerang)` so effects (Multi/Fire/Ice/Explosive) can mutate the just-spawned boomerang before flight.

### Boomerang (`Scripts/Boomerang/Boomerang.cs`)

Two-state (Flying/Returning) physics object. Drives itself via `Rigidbody.MovePosition` in `FixedUpdate` — uses `Reflect` on Wall collisions (up to `maxBounces`), `StartReturning` past `maxDistance`, and is caught when within `catchRadius` of owner. Charge throw scales `force` AND `maxDistance` (`maxDistanceOverride`). `MeleeController` parries by calling `Reflect(...)` and reassigning owner. Status effects + explosions are post-hit power-up modifiers, not core flight logic.

### HUD / Transitions / Settings

`HUDBootstrap` is `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` — it spawns `GameHUDOverlay`, `SettingsScreen`, and `IrisTransition` on a `DontDestroyOnLoad` GameObject. No scene wiring needed; **do not also place these in the scene** or you'll get duplicates. HUD/SettingsScreen receive `[Inject]` because the scope is in the loaded scene.

### Pooling

`PrimitivePool` (`Scripts/Pooling/PrimitivePool.cs`) is a static pool for runtime-spawned `GameObject.CreatePrimitive` cubes/spheres (smoke, splat chunks). Use `AcquireSphere/Cube` + `ReleaseAfter(seconds)` instead of `Instantiate` + `Destroy` for VFX primitives. `YieldCollection` (`Scripts/Utils/YieldCollection.cs`) caches `WaitForSeconds` — prefer `YieldCollection.WaitForSeconds(t)` over `new WaitForSeconds(t)`.
